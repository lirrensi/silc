## Context
Current build wiring is split across `scripts/hatch_build.py`, `scripts/build_tui.sh`, `scripts/build_tui.ps1`, and `.github/workflows/build-tui.yml`.

Important current behavior:

- `silc/__main__.py` still discovers the native TUI via `tui_client/dist` and uses `sys.argv[0]`-based path logic at import time.
- `silc/daemon/manager.py`, `silc/api/server.py`, and `silc/utils/shell_detect.py` already load static assets from `Path(__file__)`-relative `static/...` paths.
- `static/web` exists in the repo and must be bundled into the final executable.
- `static/manager` is generated by the web UI build and must also be bundled.
- `scripts/build_tui.sh` and `scripts/build_tui.ps1` build the Rust TUI into `tui_client/dist/`.
- `.github/workflows/build-tui.yml` only publishes the Rust TUI binary today; it does not build the Python app into a single executable.

For Nuitka onefile, the final binary must include the Python package, `static/web`, `static/manager`, `static/scripts`, and the Rust TUI binary directory.

## Steps

### Step 1: Add Nuitka build staging and packaging script
Create a new build script under `scripts/` that performs these actions in order:

1. Build the manager web UI into `static/manager` by reusing the existing web build flow.
2. Build the Rust TUI into `tui_client/dist` for the current platform.
3. Stage the bundle inputs into a temporary directory that contains:
   - `silc/`
   - `static/web/`
   - `static/manager/`
   - `static/scripts/`
   - `bin/` containing the Rust TUI binary
4. Run `python -m nuitka --onefile` against `silc/__main__.py` and include the staged directories as data directories.
5. Write the final executable into a predictable `dist/` directory at the repository root.

The script must work from the repository root and must not depend on `cd`-relative shell state.

✅ Success: running the build script produces a `dist/` binary for the current platform and the binary name is stable.
❌ If failed: fix the staging paths or the Nuitka command line before moving on.

### Step 2: Make the CLI resolve bundled assets in Nuitka mode
Edit `silc/__main__.py` so runtime asset lookup works in both source mode and Nuitka onefile mode.

Required behavior:

- use the Nuitka bundle directory when looking for bundled `static` and `bin` content
- keep a source-mode fallback for development runs from the repository
- stop depending on `sys.argv[0]` for bundled data discovery
- keep the current takeover prompt and native TUI launch flow intact

If a helper is needed, add it in `silc/__main__.py` or in a new small runtime-path helper module under `silc/`.

✅ Success: the CLI finds bundled assets from the extracted Nuitka directory and still works from source checkout.
❌ If failed: adjust the bundle-root logic until the same code path resolves both environments.

### Step 3: Replace the current release workflow with a full Nuitka matrix
Create or replace a GitHub Actions workflow so a release tag builds the full SILC executable per platform.

The workflow must:

- build the web UI
- build the Rust TUI
- install Nuitka
- run the same packaging command used locally
- upload the resulting platform binary as a release asset

Use a matrix that covers the real release targets the project intends to ship.

✅ Success: the workflow can produce per-platform Nuitka binaries and attach them to a GitHub Release.
❌ If failed: simplify the matrix until each target builds cleanly in GitHub Actions and `act` on Linux.

### Step 4: Add a copy-paste install script for release downloads
Replace the old PATH installer flow with a simple install script that downloads the latest release asset and places it somewhere on the user PATH.

The script must:

- detect the current platform
- resolve the correct release asset name
- download the binary from GitHub Releases
- write it to a user-writable bin directory
- mark it executable on Unix-like systems

The install script must not require a repo checkout.

✅ Success: a user can paste the script into a shell and end up with a runnable `silc` command.
❌ If failed: reduce the script to a single-platform implementation first, then expand.

### Step 5: Verify local build output and startup behavior
Run the local build path end-to-end and verify the produced binary starts.

Verification must check:

- the binary file exists in `dist/`
- the binary prints help or starts cleanly
- the binary can locate bundled `static/web` and the Rust TUI binary directory

If the environment cannot complete the full build, capture the exact failing command and stop there.

✅ Success: the packaged binary launches and resolves its bundled assets without source-tree assumptions.
❌ If failed: report the exact build or runtime error and do not proceed to release automation.
